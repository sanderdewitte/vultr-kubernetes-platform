# GitOps

## Deployment model

This repository contains three main categories of configuration:

```text
GitHub repository
├── infra/
├── platform/
└── apps/
```

Pulumi and Argo CD have separate responsibilities.

Pulumi manages infrastructure and the Kubernetes resources required before GitOps-managed workloads can run.

Argo CD manages the shared platform components and application workloads that are reconciled continuously from Git.

## Pulumi responsibilities

Pulumi manages:

- Vultr Kubernetes Engine (VKE)
- Vultr DNS
- Kubernetes namespaces
- Platform and application Secrets
- PostgreSQL roles and databases
- Argo CD `Application` resources
- Generated Helm parameters that contain deployment-specific values

Examples of deployment-specific values generated by Pulumi include:

- Application hostnames
- TLS Secret names
- Database identifiers
- OpenID Connect (OIDC) provider values

## Argo CD responsibilities

Argo CD manages:

- Shared platform components
- Helm-based applications
- Application configuration stored in Git
- Continuous reconciliation with the configured Git revision
- Pruning of resources removed from Git
- Self-healing of managed resources that drift from the desired state

Argo CD reads the remote Git repository, not the local working tree.

## Platform components

The root Argo CD `Application` watches the `platform/` directory.

Current shared platform components include:

- Traefik
- cert-manager
- cert-manager Vultr webhook
- CloudNativePG

These components are reconciled from Git after the root application has been bootstrapped.

## Application deployment

Pulumi creates one domain-aware Argo CD `Application` for every configured application deployment.

For Helm applications, the generated Argo CD `Application` uses multiple sources:

1. the upstream Helm chart repository
2. this Git repository for `apps/<application>/values.yaml`

The Git source tracks the `main` branch.

Pulumi supplies deployment-specific Helm parameters in the generated Argo CD `Application`.
Argo CD combines those parameters with the reusable values stored in Git and deploys the upstream Helm chart.

Automated synchronization is enabled with pruning and self-healing.

## Change workflows

The exact workflow depends on which layer owns the change.

### Infrastructure-only change

Changes that affect only Pulumi-managed infrastructure are applied with Pulumi:

```text
Edit infra/
  ↓
pulumi preview --diff
  ↓
pulumi up
```

Examples include:

- VKE configuration
- Vultr DNS
- Kubernetes Secrets
- PostgreSQL resources
- generated Argo CD `Application` specifications

If the same change also modifies files tracked by Argo CD, the Git changes must still be committed and pushed.

### Platform change

Changes under `platform/` are GitOps-managed:

```text
Edit platform/
  ↓
Review the Git diff
  ↓
Commit and push
  ↓
Argo CD reconciles
```

A `pulumi up` is normally not required unless the change also affects Pulumi-managed prerequisites.

### Application change

Application work can span both Pulumi and Argo CD.

Changes to `apps/<application>/values.yaml` are GitOps-managed and require only a commit and push.

Changes to the application catalog in `apps/apps.yaml` or to domain application configuration in `infra/Pulumi.<stack>.yaml` can affect Pulumi-managed resources or the generated Argo CD `Application`.i

For those changes, use:

```text
Edit configuration
  ↓
pulumi preview --diff
  ↓
pulumi up
  ↓
Verify the result
  ↓
Commit and push
  ↓
Argo CD reconciles the Git-backed sources
```

During the short interval between `pulumi up` and the Git push, an Argo CD `Application` can legitimately reference the previous Git revision while already containing a locally generated specification change.

This temporary mismatch should disappear after the changes are committed, pushed and reconciled by Argo CD.

## Verify Git revisions

Use:

```bash
./scripts/shell/argocd-git-revision-check.sh
```

to compare the Git revision currently reported by Argo CD with the local Git `HEAD`.

Without arguments, the script checks all Argo CD applications:

```bash
./scripts/shell/argocd-git-revision-check.sh
```

`--all` is equivalent and may be used explicitly:

```bash
./scripts/shell/argocd-git-revision-check.sh --all
```

To check one application:

```bash
./scripts/shell/argocd-git-revision-check.sh homarr-example-com
```

The output includes:

- application name
- Argo CD health status
- Argo CD sync status
- deployed Git revision
- whether that revision matches local `HEAD`

For multi-source applications, the script identifies the Git source rather than the upstream Helm chart source.

Applications that contain only a chart source and no Git source are reported as:

```text
CHART ONLY
```

The script returns:

```text
0  All checked applications match local HEAD
1  One or more checked applications differ
2  Usage or runtime error
```

A fully reconciled platform should normally end with all Git-backed applications showing:

```text
MATCH
```

## Verify application health

Matching Git revisions does not by itself prove that workloads are healthy.

After a deployment, also verify the relevant Argo CD application and Kubernetes resources.

For example:

```bash
kubectl get application <application-name> -n argocd
kubectl get pods -n <application-namespace>
```

A healthy application should normally report:

```text
SYNC STATUS    HEALTH STATUS
Synced         Healthy
```

Additional application-specific checks may also be appropriate.

## Git as the long-term desired state

Pulumi can generate and apply Argo CD `Application` specifications from the local configuration, but Git remains the source used by Argo CD for Git-backed platform and application content.

Therefore, a successful `pulumi up` does not replace the need to commit and push corresponding repository changes.

The intended steady state is:

```text
local HEAD
    =
remote main
    =
Git revision reported by Argo CD
```

Once that state is reached and the relevant applications are `Synced` and `Healthy`, the platform is fully reconciled.
