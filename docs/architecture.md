# Architecture

## Overview

The platform is a small, low-cost, multi-domain Kubernetes environment on Vultr Kubernetes Engine (VKE).

Pulumi manages infrastructure and application prerequisites. Argo CD manages shared platform components and application deployments from Git.

The platform separates:

- shared cluster infrastructure, such as Traefik, cert-manager and PostgreSQL
- domain-scoped applications, such as Authentik and Homarr

Applications are defined once in the application catalog and can then be enabled independently for each configured domain.

## Traffic flow

```text
Vultr DNS
  ↓
Single VKE worker node public IP
  ↓
Node host ports 80 and 443
  ↓
Traefik ingress controller
  ↓
Kubernetes Ingress
  ↓
ClusterIP Service
  ↓
Application Pods
```

Traefik is the only component exposed directly on the worker node.

Applications use `ClusterIP` Services and rely on Traefik for external access.

## Traefik port model

```text
Node port 80  → container port 8000
Node port 443 → container port 8443
```

The Traefik container listens on unprivileged ports while Kubernetes maps the public node ports through `hostPort`.

The Helm chart configuration explicitly defines `exposedPort` values so redirects advertise public ports 80 and 443 rather than internal ports 8000 and 8443.

Because the platform has one worker node and Traefik uses host ports, Traefik uses a `Recreate` deployment strategy. This avoids blocked rolling updates when a replacement Pod cannot bind ports already in use by the existing Pod.

## DNS model

Pulumi manages Vultr DNS records for each configured domain.

A domain can request an apex record, a wildcard record or both. A typical configuration produces:

```text
example.com      A      <VKE worker node public IP>
*.example.com    CNAME  example.com
```

Pulumi derives the current worker node public IP from the VKE node pool.

If the node is replaced and receives a new public IP address, `pulumi up` updates the managed DNS records.

The wildcard record allows domain applications to use hostnames such as:

```text
auth.example.com
www.example.com
```

without requiring a separate DNS record for every application.

## Certificate model

cert-manager is installed as a shared platform component.

The platform uses Let's Encrypt with ACME DNS-01 validation through the Vultr webhook.

Two ClusterIssuers are provided:

```text
letsencrypt-staging
letsencrypt-production
```

Applications request certificates through Ingress annotations and TLS configuration.

The Vultr API token is stored outside Git and is written to Kubernetes by Pulumi.

## Multi-domain application model

The platform is designed to host multiple independent domains on the same Kubernetes cluster.

Applications are defined centrally in:

```text
apps/apps.yaml
```

This application catalog describes application capabilities and defaults, including:

- whether a dedicated namespace is required
- database requirements
- upstream Helm chart repository and version
- default hostname prefix
- application Secret requirements
- Helm parameter paths for deployment-specific values
- optional OpenID Connect (OIDC) authentication support

Applications are then enabled per domain in `Pulumi.<stack>.yaml`.

For example:

```yaml
config:
  vultr-kubernetes-platform:domains:
    - name: example.com
      apex: true
      wildcard: true
      applications:
        - authentik
        - homarr:
            authentication:
              oidc:
                identity_provider: authentik
```

The application catalog describes what an application needs, while the stack configuration describes where and how that application is deployed.

Domain-specific values are generated by Pulumi rather than stored in application `values.yaml` files. These include hostnames, TLS Secret names, database identifiers and OIDC provider URLs.

## Domain-scoped identity

Authentik is deployed as a domain application rather than as a single shared identity service for all domains.

This keeps authentication within the same domain boundary. For example:

```text
www.example.com  →  auth.example.com
www.example.org  →  auth.example.org
```

An application can declare an OIDC identity provider in its per-domain configuration. Pulumi then derives the provider hostname, issuer URL, logout URL and other configured Helm parameters for that application.

OIDC client credentials remain domain- and application-specific Secrets.

This allows the application integration to be generated consistently while authorization policy remains under the control of the identity provider and application.

## PostgreSQL model

CloudNativePG runs one shared PostgreSQL cluster in the platform database namespace.

Applications can request database resources through `apps/apps.yaml`.

For every database-enabled application and domain combination, Pulumi creates:

- a dedicated PostgreSQL login role
- a dedicated database owned by that role
- a database credential Secret in the platform database namespace

The role is not a PostgreSQL superuser.

For applications that require a complete PostgreSQL connection URL, the catalog can additionally request a namespace-local Secret containing a URL such as:

```text
postgresql://<user>:<password>@<cluster-service>:5432/<database>
```

This lets applications consume the connection format expected by their Helm chart without exposing shared database credentials.

The PostgreSQL cluster itself is shared, but application databases, roles and credentials are isolated per domain/application combination.

## Secrets model

Secret values are kept outside Git and loaded by Pulumi from the local secrets configuration.

Pulumi creates Kubernetes Secrets according to their required scope.

Platform-level examples include:

- Vultr credentials used by the cert-manager webhook
- PostgreSQL bootstrap and superuser credentials

Domain/application-level examples include:

- PostgreSQL passwords
- application encryption keys
- OIDC client credentials

Secrets used directly by an application are normally created in that application's namespace.
Secrets required by CloudNativePG to manage database roles are created in the platform database namespace.

Pulumi marks generated Secret resources as protected to reduce the risk of accidental deletion.

## Application deployment model

For every enabled domain/application combination, Pulumi creates the required prerequisites, which can include:

- a dedicated namespace
- Kubernetes Secrets
- PostgreSQL resources
- an Argo CD `Application`

Argo CD then performs the application deployment.

For Helm applications, the generated Argo CD `Application` uses multiple sources:

1. the upstream Helm repository containing the application chart
2. this Git repository containing `apps/<application>/values.yaml`

Pulumi supplies deployment-specific Helm parameters, while the repository-hosted values file contains reusable application configuration.

Argo CD tracks the `main` branch and uses automated synchronization with pruning and self-healing.

This creates a deliberate ownership boundary:

```text
Pulumi
  ├── cloud infrastructure
  ├── DNS
  ├── namespaces
  ├── Secrets
  ├── database resources
  └── Argo CD Application resources

Argo CD
  ├── shared platform components
  └── application workloads from Git and upstream Helm charts
```

## Cost and availability trade-off

The platform intentionally avoids a managed load balancer.

This reduces monthly cost but means the ingress layer is not highly available.

If the single worker node is unavailable, external access to applications is unavailable.

The Pulumi configuration validates that this architecture is used with exactly one worker node.

The ingress architecture should be revisited if the platform grows beyond one worker node.

## Resource naming

Resources are named programmatically according to the scope in which they must be unique.

### Cluster-wide and shared-namespace resources

Resources that are cluster-wide or share a namespace with resources for multiple domains or applications include sufficient context to guarantee uniqueness.

Examples:

```text
authentik-example-com-postgresql
homarr-example-com-postgresql
```

### Namespace-local resources

Resources created inside a dedicated application namespace do not repeat the domain name because the namespace already provides that uniqueness.

For example:

```text
Namespace:
homarr-example-com

Resources:
homarr-postgresql-url
homarr-secret-encryption-key
homarr-oidc-credentials
```

This keeps resource names concise and predictable.

It also allows application-specific files such as `apps/<application>/values.yaml` to remain independent of deployment-specific details such as domain names.
The values file describes reusable application configuration, while Pulumi supplies domain-specific values when generating the deployment.
